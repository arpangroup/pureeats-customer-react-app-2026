Active-address resolution

How PureEats picks what to show as the customer's delivery location, and how every step of that is backend-configurable. Companion to docs/location-resolution/README.md — this page is just the two flows as pictures, with the config/API reference alongside.

1 · Detection — which sources get a value at all

flowchart TD
    A["App boot\n(LocationAutoDetectBootstrap)"] --> B{"AppConfig loaded?"}
    B -->|"not yet"| C["Use local\ndefaultLocationResolutionConfig"]
    B -->|"yes"| D["Use backend\nlocationResolution*Priority"]
    C --> E{"isAuthenticated?"}
    D --> E
    E -->|"yes"| F["priority = AuthenticatedPriority\nfallback = AuthenticatedFallbackLabel"]
    E -->|"no"| G["priority = GuestPriority\nfallback = GuestFallbackLabel"]
    F --> H{"'gps' or 'ip'\nin priority?"}
    G --> H
    H -->|"neither"| Z["Nothing to auto-detect\n(only 'saved' can show)"]
    H -->|"'gps' present"| I{"navigator.permissions\n.query('geolocation')"}
    I -->|"granted"| J["getCurrentPosition()"]
    J --> K["GET /geo/reverse-geocode\n(Nominatim proxy, cached)"]
    K --> L["detectedLocations.gps = label"]
    I -->|"denied"| M["Show dialog:\nOS/browser settings steps"]
    I -->|"prompt"| N["Show dialog:\n'Allow location access'"]
    I -->|"unsupported"| O
    M --> O["GET /geo/ip-location\n(ip-api.com proxy, cached)"]
    N --> O
    H -->|"only 'ip' present"| O
    O --> P["detectedLocations.ip = label"]
decision point network call (backend-proxied, cached) resolved value written to context

2 · Display — which resolved value actually shows

flowchart TD
    A["resolveActiveLocationLabel()"] --> B{"'saved' next in\npriority list AND\nactiveAddress set?"}
    B -->|"yes"| C["Show saved address's tag\n(e.g. 'Home')"]
    B -->|"no"| D{"'gps' next AND\ndetectedLocations.gps set?"}
    D -->|"yes"| E["Show GPS-resolved address"]
    D -->|"no"| F{"'ip' next AND\ndetectedLocations.ip set?"}
    F -->|"yes"| G["Show 'Near <city>'\nor IP-resolved address"]
    F -->|"no, list exhausted"| H["Show fallbackLabel\n('Other' / 'Set your location')"]

Same function, evaluated fresh on every render — as sources resolve asynchronously (GPS/IP calls take time), the label upgrades itself automatically without any extra "refresh" step.

Config — backend-editable, frontend-defaulted

Four fields inside the existing AppConfig blob (GET /api/v1/app-config, editable via PUT /api/v1/admin/app-config):

{
  "locationResolutionAuthenticatedPriority": ["saved", "gps", "ip"],
  "locationResolutionGuestPriority": ["gps", "ip"],
  "locationResolutionAuthenticatedFallbackLabel": "Set your location",
  "locationResolutionGuestFallbackLabel": "Other"
}
Frontend fallback: src/config/locationResolution.ts's defaultLocationResolutionConfig mirrors these exact defaults — used until /app-config resolves, and per-field for any older backend missing one of them.

API reference

EndpointAuthPurpose
GET /api/v1/app-configPublicThe priority/fallback config above, alongside every other feature flag
PUT /api/v1/admin/app-configAdminEdits it
GET /api/v1/geo/ip-locationPublicIP → coarse {latitude, longitude, city, country}, ip-api.com proxy, cached server-side
GET /api/v1/geo/reverse-geocode?lat=&lon=PublicCoordinates → {displayName, city, state, country, postcode}, Nominatim proxy, cached server-side

Design decisions summary

QuestionDecisionStatus
Reverse geocode: frontend calls Nominatim directly, or via backend?Backend proxy — required User-Agent header, dodges ad-blocker interference, enables shared server-side caching, provider swap without a frontend deploy.Implemented
Resolve location at app load, or wait for Home page mount?App load — mounted in App.tsx, not HomePage, so the header pill is more likely already correct on first paint.Implemented
Should restaurant listing require lat/lon, or fall back to backend IP resolution?Hybrid recommended: accept optional lat/lon query params, backend resolves IP itself when absent (reusing IpGeolocationService) rather than erroring or returning unsorted.Recommended only — see README
