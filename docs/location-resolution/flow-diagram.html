Who decides “here”?

Four independent sources can claim the customer app's home-page location pill — gps, ip, saved, picked. Which one actually wins is a single config-driven priority walk, resolveActiveLocation(), evaluated separately for signed-in customers and guests. This page traces how each source gets populated, and how the winner is picked. Companion to README.md in this same folder, which has the full write-up, API reference, and design-decision log.

Capturing a location

runs once per app boot

    A["App boots or page refreshes"] --> B["LocationProvider hydrates from localStorage:\nactiveAddress · detectedLocations.gps/.ip · pickedLocation"]
    B --> C["AppConfigProvider fetches GET /app-config\n(local defaults used until it resolves)"]
    C --> D{"Signed in?"}
    D -- yes --> E["LocationBootstrap: no activeAddress yet?\nGET /users/me/addresses, auto-select the default"]
    D -- no --> F["Nothing to bootstrap —\na guest has no saved address"]
    E --> G
    F --> G
    G["useLocationAutoDetect runs once,\nmounted above the router — a return to Home never re-triggers it"]
    G --> H{"This auth state's priority list\ncontains 'gps' or 'ip'?"}
    H -- neither --> Z["Nothing auto-detected this session"]
    H -- "'gps' listed" --> I{"navigator.permissions\n.query('geolocation')"}
    I -- granted --> J["getCurrentPosition()"]
    J --> K["GET /geo/reverse-geocode"]
    K --> L["detectedLocations.gps set"]
    I -- denied --> M["Show permission dialog,\nrun IP fallback in background"]
    I -- prompt --> N["Show 'Allow location' dialog,\nrun IP fallback in background"]
    M --> O
    N --> O
    H -- "only 'ip' listed" --> O
    O["GET /geo/ip-location"] --> P["detectedLocations.ip set"]

detectedLocations.gps and .ip live in separate slots — never merged into one “last resolved,” so a priority list that puts ip ahead of gps still works correctly. Both are cached to localStorage (key pureeats.lastDetectedLocations) purely so the pill has something real to show on the very next paint, before this sequence finishes again.

Confirm on the map
Drag the pin or search a place, tap Confirm location → setPickedLocation().
Tap a recent search
Already a confirmed choice — sets pickedLocation immediately, no confirm step.
Choose a saved address
Sets activeAddress and clears pickedLocation, so the two never fight.

All three write to localStorage (pureeats.pickedLocation / pureeats.activeAddress) — the only source not touched by useLocationAutoDetect's background refresh above, which is exactly why a manual pick survives a refresh instead of being silently overwritten by a fresh GPS fix.

The numbered order above is today's default config, not a fixed rule — resolveActiveLocation() just walks whatever array locationResolution*Priority holds, so reordering it (see below) reorders these boxes with no code change. A guest's list has no saved step at all — they have nothing saved to check.

Default configuration

defaultLocationResolutionConfig
locationResolutionAuthenticatedPriority
  1. 1 gps
  2. 2 ip
  3. 3 saved
  4. 4 picked
locationResolutionGuestPriority
  1. 1 gps
  2. 2 ip
  3. 3 picked
A live backend's actual values may differ from this shipped default — check any running instance's admin panel at Settings → Customer Application → Active‑location priority, or GET /api/v1/app-config directly. Reorder either list any time to make a saved/picked address win over live GPS again, or drop a source entirely to stop it being tried — no redeploy needed either way.
